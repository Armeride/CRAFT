# 작업 011 측정

[작업 011](011-sourcebook-performance.md)의 기준 측정과 그 뒤 최적화 단계별 측정 결과다. 결과 1~4와 병목 후보는 변경 전 기준이다. 기준 측정 커밋은 앱 동작을 바꾸지 않았고, 호출 횟수와 시간을 세는 계측과 측정 도구만 추가했다. 최적화 결과는 [아래](#최적화-결과)에 있다.

## 측정 환경과 방법

- WSL2 Linux 6.18, Node 24.21.0, 24코어, 메모리 7GB. 측정은 한 번에 하나씩 순차 실행했다.
- 계측: [instrumentation.ts](../../packages/domain/src/instrumentation.ts)가 스레드별로 호출 횟수, 누적 시간, 규모를 센다. 대상은 다음과 같다.
  - `fs.captureFiles.*`: 작업 폴더 전체 읽기
  - `git.readCommittedFiles.*`: 커밋 트리 전체 읽기
  - `project.parse`: 스냅샷 파싱·검증
  - `git.<명령>`, `git.process`: Git 프로세스 실행
  - `state.read|write.<정의>`: 런타임 상태 파일과 쓰기 저널
  - `lock.held|busy.<종류>`: OS 잠금 보유 시간과 거절 횟수
- 색인 worker 스레드 안의 작업은 기존 manifest `prepareMs`·`sqliteMs`로만 본다.
- `npm run bench:index`: 기존 1,000요소·10,000리비전 측정. 단계별 계측값을 함께 출력한다.
- `npm run bench:sourcebook -- [--entities N --revisions R --characters C --progress 파일]`: 설정집 한 세션을 모델 없이 HTTP 라우트와 MCP 도구 경로로 재현한다.
  - 가져오기 → 작업 열기 → MCP 조회 4회 → 인물 초안 C건(초안마다 원본 PNG 1장, 인접 인물 간 고정 참조 C-1건, 매번 `context.build` 재호출) → `project.validate` → 검토 화면 → 통합 준비 → 적용 → 첫 이미지
  - 기본값은 원고 12장, PNG 1.1MB 6장이다. 모델 대기 시간은 0이므로 측정값은 모두 CRAFT 처리 시간이다.

## 결과 4 — 기능 한계: 큰 프로젝트에서 통합 불가

- 통합 검토 diff의 대부분은 체크포인트마다 생기는 `tasks/<task>/checkpoints/cp_*-inputs.yaml`이다. 100요소에서 파일당 33.5KB였고, 초안 6건 세션에 9개가 생겼다.
- 이 파일은 요소 수에 비례해 커진다. 1,000요소에서는 초안 1건짜리 세션도 1MB 표시 한도([integration.ts:124](../../packages/tasks/src/integration.ts#L124))를 넘는다.
- 결과적으로 1,000요소 규모의 설정집에서는 AI 초안을 통합할 수 없다. 성능 개선과 별개로 판단이 필요하다. 선택지는 diff에서 입력 manifest 제외, 요약 표시, 한도 조정이다.

## 병목 후보 (실측 근거 순)

1. **전체 작업 폴더 캡처의 반복.** 모든 단계 시간의 70~98%를 차지한다.
   - 캡처 1회가 21,007파일에서 약 3.3초다. 파일마다 `lstat`·`realpath`·`fstat`를 각 2회, open/read/close를 하고 SHA-256, base64, UTF-8 변환을 거친다([files.ts](../../packages/project-fs/src/files.ts)).
   - 이것이 MCP 조회 1회에 6회, 초안 저장 1회에 21회, 가져오기에 56회, 통합 준비에 67회 반복된다.
   - 소규모 CPU 프로파일에서 파일 시스템 호출 자체 시간이 약 41초로, 사용 CPU의 29%였다.
   - 효과가 큰 방향은 두 가지다.
     - 요청 단위로 캡처를 한 번만 하고 공유한다.
     - (ino, size, mtime, ctime)이 같은 파일은 digest를 재사용한다.
2. **편집마다 전체 캡처와 저널 재기록** ([writer.ts](../../packages/project-fs/src/writer.ts) `finish()`).
   - 편집 하나마다 `captureFiles(root, false)`를 하고, PNG base64가 든 저널 전체를 JSON 직렬화·YAML 재검증해 다시 쓴다. 편집 수 × (파일 수 + 저널 크기)에 비례하는 이차 비용이다.
   - 통합 준비(편집 61건)에서 저널 쓰기가 64회, 1,013MB였다.
3. **적용이 끝난 쓰기 저널을 매 호출마다 전부 다시 읽음** (`assertNoPending`, `assertSavedRecords`).
   - 저널은 지워지지 않는다. 읽을 때마다 YAML 파싱, JSON 파싱, Ajv 검증을 모두 거친다.
   - `context.build` 1회당 읽기가 72회 28MB에서 180회 272MB로 늘었다. 세션이 길어질수록 계속 늘어난다.
   - 색인 `status()`도 이 검사를 거치므로 모든 조회에 영향을 준다.
4. **파싱마다 스키마 컴파일과 YAML 전체 파싱** ([project.ts](../../packages/project-fs/src/project.ts) `parseProject`).
   - 호출마다 `new SchemaValidator()`(새 Ajv 인스턴스)를 만들어 스키마를 다시 컴파일한다.
   - 초안 저장 1회에 12~13회, 15~20초다.
   - 불변인 커밋 스냅샷(`loadCommittedProject`)도 캐시 없이 다시 읽고 파싱한다.
5. **Git 프로세스 수.**
   - `runGit`은 `rev-parse`/`symbolic-ref`가 아닌 명령마다 필터 설정 확인용 `git config`를 하나 더 띄운다. 통합 준비에서는 315개 중 134개였다.
   - 마이그레이션 커밋은 파일마다 `hash-object`와 `ls-files`를 순차로 실행한다.
   - 프로파일에서 `spawn` 동기 비용이 11.4초(8%)였다. Windows에서는 더 클 것으로 예상한다.
6. **메모리와 GC.**
   - 파일 내용을 base64 문자열로 여러 번 복제한다. 캡처, worker 전달, 저널에서 모두 그렇다.
   - 프로파일상 GC가 사용 CPU의 21%였다. 최대 상주 메모리는 2.76GB다.
7. **색인 worker** (전체 재파싱·재분석, 루프 안의 statement 준비).
   - 21,007파일에서 준비 1.5초, SQLite 0.1~0.5초다. 현재는 1~3번에 가려 우선순위가 낮다.

### 남은 병목

- **캡처 횟수.** 초안 저장 13.5초 중 7.8초, MCP 조회 4.0초 중 3.4초가 여전히 전체 캡처다. 캡처 1회는 빨라졌지만, 요청마다 변경 여부를 확인하려고 전체 폴더를 다시 훑는 구조는 그대로다.
- **색인 목표.** exact 0.2초, 증분 1초는 캡처 없이 변경을 알아내는 방식(파일 감시나 쓰기 경로의 변경 epoch)이 있어야 가능하다. 일관성 보장 방식이 바뀌므로 설계 결정이 필요하다.
- **통합 준비의 Git 프로세스.** 311개를 실행한다(후보 5). 남은 27.9초의 상당 부분이다.
- 후보 6(base64 복제)과 7(색인 worker 재파싱)은 다루지 않았다.

## 측정의 한계

- 측정은 한 장비에서 했다. 1,000요소 세션을 초안 6건과 1건으로 두 번 실행했는데, 공통 단계(원본 열기~첫 초안 저장)의 시간 차이는 3% 이내였다.
- 실제 소설 패키지가 아니라 합성 fixture다. 원고 12장, PNG 1.1MB 6장, 문서 형식 YAML이 아닌 JSON 텍스트다.
- MCP 호출 사이에 0.5초 간격으로 실행 상태를 조회하는 요청이 측정값에 섞여 있다. 이 요청은 저널이나 캡처를 읽지 않는다.
- `WORKTREE_BUSY` 거절은 단일 사용자 순차 실행이라 0회였다. 동시 작업 시나리오는 측정하지 않았다.
- Windows는 측정하지 않았다.
